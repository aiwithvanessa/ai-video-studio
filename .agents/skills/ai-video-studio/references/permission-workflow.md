# Low-friction project work

## Fix the boundary once

Before setup or the first edit, inspect the active Codex workspace/writable-root declaration. Changing shell cwd does not change that declaration. Compare the actual studio folder with those roots using scripts/check-workspace.mjs --project <studio-folder> --workspace-root <declared-writable-folder> (repeat roots when needed). No roots means unknown, not permission granted. The helper does not edit permissions or establish every protected-path/network exception.

If the studio is outside the writable scope, explain the mismatch once and ask the user to open that studio folder as the active Codex project, or grant that narrowly scoped folder through supported controls. Preserve progress and resume. Do not proceed by requesting elevated access for every caption, brief, effect or render. A sibling test project outside an owner workspace needs its own project context; do not move/copy private projects to make prompts disappear. Keep the future bootstrap target equal to the empty folder the recipient actually opened. Do not silently choose an external sibling target.

## A requested edit authorizes its implementation

Treat “edit this video”, an accepted brief, or a revision request as authorization for the ordinary work needed to produce a reviewable local draft: import explicitly supplied readable media, inspect metadata/frames, maintain folders/briefs/state, use established local transcription for requested captions, implement captions/graphics/zooms, run checks, start/reuse preview, render draft MP4s and fix in-scope implementation failures. Do not ask “may I add captions?”, “may I update the brief?”, “may I render the draft?” or obtain the same consent again. Use the default sandbox for these operations inside the project. Escalate only when the actual boundary or a concrete failure requires it; never set require_escalated reflexively for local editing. Source code, generated frames, scratch audio and verification should use project-local/allowed temp paths. Protected .agents/.codex/.git paths can still require approval even within a writable root.

Setup request authorizes the supplied project's required local setup within the stated scope. Explain the planned dependency/browser/model downloads, approximate known sizes and local CPU approach together before execution. Inspect existing dependencies/tool/model integrity first; reuse valid installed versions instead of installing again. When setup already authorized these steps, do not add a conversational permission question for each command. The platform may separately enforce network/installer approvals; batch coherent setup commands and use narrowly scoped persistent command approvals only when actually offered/appropriate. Do not request broad arbitrary-shell permissions. New unrelated/optional tools, unapproved services or larger models are outside this standing scope.

Ask short creative questions only for decisions that affect the result or essential missing assets; use approved defaults for optional gaps. Describe significant graphics/effects in the draft/brief for review instead of blocking each routine effect on pre-approval. Offer plain-language changes. Never infer a creative decision from a system Allow click.

## Keep real approval boundaries

User review of the initial brand/style proposal and explicit approval of the current video before final export remain. Revisions invalidate export approval. If the user has already approved the current version and asked to export, run the guarded export; do not ask permission again. Do not publish, upload private media, change global settings, install globally/admin tools, delete unrelated files, expand access or spend money without appropriate authorization. An OS/managed-policy denial is a real blocker, not something instructions or a cached approval can bypass.

Current official controls: workspace-write permits routine project-local work; outside writes and restricted network operations may need approval. The desktop permissions control can offer Approve for me, which routes eligible requests to automatic review while retaining the sandbox. Its availability/decisions are not guaranteed. Offer it as an optional user choice, not an automatic configuration change or a prerequisite; do not recommend Full access/YOLO/never as the starter default. See official documentation (consult live versions when advising): https://learn.chatgpt.com/docs/agent-approvals-security and https://learn.chatgpt.com/docs/sandboxing . Project instructions cannot promise zero prompts or exactly one installation prompt.

## Resume efficiently

Read state and resume the missing stage. Reuse existing approved brand choices, unchanged transcript/model/tool installation and the correct owned preview server. Run checks appropriate to changes, not full setup or all checks after every small data adjustment. Group independent checks; after related edits run the relevant checks and one complete draft render. Do not render for documentation-only updates. Retain errors and diagnose before retrying the same failed path; report the actual time/failure evidence rather than claiming speed from instruction changes alone.

Maintained render/preview commands use scripts/project-temp.mjs for process-local TEMP/TMP under .local/tmp, avoiding invalid Windows sandbox temp paths containing ! without changing global settings. A browser startup or socket denial may still require one scoped render approval; do not use that as a reason to elevate all caption/brief edits.
